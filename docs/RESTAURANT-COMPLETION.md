## Reservation integrity

Availability uses a repeatable-read PostgreSQL snapshot of actual table capacity, activation, reservations and open checks. Start times come only from the configured weekday window, start interval, duration/turnover, lead time and advance-booking horizon. No schedule or available slots are seeded. Dates are validated as real calendar dates and converted using the restaurant's IANA timezone, independently of server/browser timezone. Skipped/ambiguous daylight-saving times are rejected. Each booking stores the promised timezone so later settings changes do not reinterpret its confirmation.

Creation locks restaurant then candidate table rows in a serializable transaction, rechecks holds/open checks, allocates a fitting table and persists CONFIRMED status. A unique idempotency key/request hash handles lost-response retries. The browser redirects to confirmation only after a successful server response. Private confirmation uses a random 256-bit fragment token; only its hash is stored. Public availability exposes no guest/contact records. No email/SMS service or success notification is simulated.

The database adds a `btree_gist` exclusion constraint over half-open table/time ranges for REQUESTED, CONFIRMED and SEATED holds. It rejects overlaps even through direct SQL and permits adjacent windows. A partial unique index also prevents two SEATED parties occupying one table, even with non-overlapping scheduled windows. Seated parties remain occupied after their scheduled end until explicitly completed; no timeout invents a free table. Existing open POS checks and seated parties conservatively block new bookings on that table until cleared, including future bookings. Tables are not automatically combined.

POS table queries now report reservation holds. Existing floor cards and table selection show held tables as Reserved. Walk-in orders cannot take a table reserved within the configured hold horizon. A specific seated-reservation link can open its own check; duplicate checks and mismatched tables/tenants are rejected. Completing that check requires the existing staff cash attestation and atomically completes the seated booking. Staff status changes validate the expected previous state. Capacity reductions/deactivation conflicting with active checks or holds are rejected.

## Configuration and migrations

1. Use a dedicated development/test PostgreSQL database; run `npm ci`, `npm run db:generate`, `npm run db:migrate`, and `npm run db:seed` following README. No dependency or external service was added.
2. Create the initial admin using private seed environment variables; there is no default password. Do not publish seed credentials. Remove the seed password after account creation.
3. Sign in at `/pos/login`, open `/admin/business`, enter the real timezone/weekly hours and review the actual tables/capacities. Set booking limits and explicitly enable reservations. Configure real address, contact, service area, legal operator and delivery rules. Missing facts remain visibly unconfigured. The source seed never enables bookings.
4. Choose sample, configured flat-fee, configured-zone or disabled delivery. Fees/minimums are entered in BDT and stored as integer poisha. The server verifies the selected zone and charges current rules; pickup remains free. Staff must verify addresses against named areas because no geocoding provider is configured.

Additive migrations are `20261030010000_reservations_business`, `20261030011000_reservation_timezone_snapshot`, and `20261030012000_seated_occupancy`. The first requires permission to install PostgreSQL's trusted `btree_gist` extension. Previous migrations are unchanged. The existing checksum/advisory-lock migration runner remains in use. Legacy reservation rows receive 90-minute windows, keep their data, and require operator review. Existing overlapping holds or duplicate seated parties require reconciliation before the constraints can be installed; migration failure does not silently delete records.

Existing API payloads continue to work with the labelled sample fee. Additions: optional checkout `deliveryZoneId`, optional staff-order `reservationId`, menu `business` configuration, and table `reservationHold`. Saved order price/fee/zone snapshots remain unchanged when settings change. Booking time windows remain unchanged when hours/timezone configuration changes.

New endpoints: public `GET /api/business`, `GET /api/reservations/availability`, `POST /api/reservations`, capability-protected `GET /api/reservations/[id]`; authenticated service `GET /api/pos/reservations`, `PATCH /api/pos/reservations/[id]`; manager/admin `GET/PATCH /api/admin/business` and `POST /api/admin/tables`. Mutations use the existing same-origin and bounded-JSON checks. Kitchen users cannot manage reservations; service staff cannot edit business/table configuration. Hiding navigation links provides no access control; server checks do.
